# common-anti-bloat

给还在长大的代码库用的**防膨胀闸** —— 给的是**能跑的命令,不是价值观**。

[English](README.md) · MIT · 作者 [wind](https://github.com/wind-c)

---

## 设计思想

绝大多数"反屎山"建议本质是一套价值观:*保持简单、多删代码、别过早抽象*。你本来就同意,
所以什么也不会改变 —— **认同是不可执行的**。

这个技能反过来:每条模式都配**一条可以直接跑的命令**和**一个该返回的数**。你不需要判断
代码"是不是有点乱",跑一下,看结果。

由此推出三条:

- **会说谎的检测器比没有检测器更糟。** 它照样返回一个数字,而数字看起来像证据。所以每条
  信号都点名了自己在哪种语言下会失效,§0 强制你**先校准再用**。
- **每个阈值都是量出来的,不是拍的。** 数字来自两个真实项目(一个 Rust ~170k 行、一个
  Python ~12k 行)。凡是推断而非实测的行,文档里明说。
- **"删什么"是一等步骤。** 清单第 7 条问这次改动能删掉什么,答不上来就得在 commit message
  里解释为什么。

## 它能抓到什么

十条信号,每条带检测命令:

| | | |
|---|---|---|
| **A1** 核心依赖未来层 | **A2** 配置声明了死路径 | **A3** 原型过期未清 |
| **A4** 入口即业务逻辑 | **A5** 为一个文件建包 | **A6** 只有一个实现的抽象 |
| **A7** 已经不成立的文档 | **A8** 为一行代码引依赖 | **A9** 同一事实两份拷贝 |
| **A10** 能通过 CI 的死代码 | | |

其中两条值得单独说 —— 它们是**行数看着正常、代码却在悄悄烂掉**的那类:

- **A9 同一事实两份拷贝。** 这不是按体积算的膨胀,是按**义务**算的:每多一份拷贝就多一条
  没有工具强制的维护责任。**写着"记得和 X 保持同步"的注释,是一份 bug 报告,不是文档。**
- **A10 通过 CI 的死代码。** 全绿的测试对它从不触碰的代码不构成任何证据。这基本是动态语言
  的问题 —— 编译器会解析导入的语言,跑编译器就够了。

## 怎么触发

模型自动调用。出现下面情况它会自己起来:

- 你担心代码膨胀、腐烂、"要变成屎山了"
- 你正要新增**一个包、一个依赖、一层抽象、一段配置、或一份设计文档**
- 你问某个 diff **本该删掉什么**

也可以直接点名调用。

## 结构

```
SKILL.md                      常驻    校准表 + 8 条前置闸 + 7 步审计
references/SIGNALS.md         按需    十条信号的完整定义与证据
scripts/dead-import-scan.py   执行时  A10 检测器，命中即退出码 1，可直接进 CI
```

分三层是因为**三种用法里有两种不需要那些信号定义**:写代码前的闸自成一体,只有审 diff 和
做审计才会翻 `references/`。

## 怎么用

**写代码前** —— 八个二元闸,答"是"意味着**停下来修**,不是停下来想。最容易被跳过的是最后
一条:*我是不是在写一个别处已经存在的事实?*

**审 diff 时** —— 同样八个闸对着改动过一遍,每个"是"就是一条要提的意见。

**周期性** —— 七步审计,最后落一份很短的 ADR 记录删了什么。**那份 ADR 是收据,不是设计文档。**

**每个项目第一次用之前** —— 读 §0,按你的语言重设阈值。A5、A8、A10 开箱即用是**错的**:
500 行在 Java 和 Python 里含义完全不同;npm 的微包文化让 A8 比 Maven 生态严厉得多;而在
`cargo check` 或 `tsc --noEmit` 已经跑着的地方,A10 几乎不存在。
